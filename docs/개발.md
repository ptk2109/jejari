# 개발

빌드, 버전, 변경 기록, 버전 내기, 시험 방법.

## 빌드

1. `brew install xcodegen`
2. 서명 Team을 `Configs/Signing.local.xcconfig`에 적는다 (커밋하지 않음): `DEVELOPMENT_TEAM = <Team ID>`
3. `xcodegen generate` (`project.yml` → `Jejari.xcodeproj`. 생성물이라 커밋하지 않음)
4. `xcodebuild -project Jejari.xcodeproj -scheme Jejari -configuration Debug -derivedDataPath build -allowProvisioningUpdates build`
5. `open build/Build/Products/Debug/Jejari.app`

- 새 파일을 추가하면 3번을 다시 한다
- 같은 Team으로 서명하면 다시 빌드해도 손쉬운 사용 권한이 유지된다. Team을 바꾸면 권한을 다시 켜야 한다

## 버전

유의적 버전(주.부.수)을 쓴다.

- 주: 저장 파일 형식이 호환되지 않게 바뀌거나 큰 변화. 1.0.0은 일반 사용자가 설치해 쓸 수 있는 첫 배포판
- 부: 기능 추가
- 수: 버그만 고침

버전은 `project.yml`의 `CFBundleShortVersionString`, git 태그 `v주.부.수`, `CHANGELOG.md`의 항목이 같아야 한다. `CFBundleVersion`은 배포할 때마다 1씩 올린다.

## 변경 기록

- 사용자가 알아챌 변경(기능 추가·변경·제거, 버그 수정)은 `CHANGELOG.md`의 `[Unreleased]`에 적는다. `main`에 들어가는 변경에는 항목이 같이 들어 있어야 한다
- 형식은 Keep a Changelog. 묶음은 추가 / 변경 / 수정 / 제거
- 사용자 입장에서 쓴다. 파일명·함수명 대신 무엇이 달라졌는지
- 내부 정리, 개발용 도구, 문서만 바뀐 것은 적지 않는다

## 버전 내기

1. `CHANGELOG.md`의 `[Unreleased]` 내용을 `[주.부.수] - 날짜` 항목으로 옮기고, 아래 비교 링크를 고친다
2. `project.yml`의 `CFBundleShortVersionString`, `CFBundleVersion`을 올린다
3. `chore: v주.부.수`로 커밋하고 PR로 `main`에 합친다 (작업 브랜치의 마지막 커밋으로, 또는 `main`에서 만든 `chore/v주.부.수` 브랜치에서)
4. `main`을 받아 태그를 붙이고 푸시한다: `git switch main && git pull && git tag -a v주.부.수 -m "v주.부.수" && git push origin v주.부.수`
5. `scripts/release.sh`: Release 빌드 → zip → Sparkle 서명 → `appcast.xml` → GitHub Release 만들기(zip, appcast.xml 첨부, 변경 기록이 본문)
   - 먼저 `scripts/release.sh --dry-run`으로 `dist/`에 만들어 보고 확인할 수 있다 (검사·업로드 없음)
   - 태그가 붙은 커밋, 깨끗한 작업 트리, 푸시된 태그, `CHANGELOG.md`의 해당 버전 항목이 없으면 멈춘다

### 자동 업데이트 (Sparkle)

- 앱은 `https://github.com/ptk2109/jejari/releases/latest/download/appcast.xml`을 하루에 한 번 확인한다. GitHub의 "Latest" Release에 붙은 `appcast.xml`이 곧 최신 버전이므로 Release를 시험판(pre-release)이나 초안으로 두지 않고, 버전 순서대로 낸다
- 업데이트 파일은 EdDSA 비밀 키로 서명한다. 공개 키는 `project.yml`의 `SUPublicEDKey`, 비밀 키는 키를 만든 맥의 로그인 키체인에 있다
  - 비밀 키를 잃으면 이미 설치한 사용자에게 업데이트를 보낼 수 없다. `generate_keys -x <파일>`로 백업하고, 다른 맥에서는 `generate_keys -f <파일>`로 가져온다
  - 도구 위치: `build/SourcePackages/artifacts/sparkle/Sparkle/bin/` (한 번 빌드하면 생김)
- 같은 Team으로 서명해야 업데이트 뒤에도 사용자의 손쉬운 사용 권한이 유지된다. `release.sh`가 Team 서명인지 확인한다
- 개발 빌드는 업데이트를 확인하지 않는다 (배포판과 번들 ID가 같아서 덮어쓰지 않게)
- 업데이트 동작 시험: Release 빌드 사본(이전 버전)과 버전을 올린 `--dry-run` 결과를 준비하고, `appcast.xml`의 파일 주소를 `http://127.0.0.1:<포트>/`로 바꿔 `python3 -m http.server`로 띄운다. `defaults write com.nam24.jejari SUFeedURL http://127.0.0.1:<포트>/appcast.xml`, `SUAutomaticallyUpdate -bool true`, 오래된 `SULastCheckTime`을 넣고 사본을 실행하면 내려받는다. 사본을 끄면 새 버전으로 바뀐다. 끝나면 `SU`로 시작하는 키를 지운다

## 시험

개발 빌드는 `jejari://` URL 명령으로 시험할 수 있다. 결과는 `~/Library/Application Support/Jejari/last-result.json`. 개발 빌드는 모든 명령을 확인 없이 받는다. 배포판은 설정의 "외부 명령" 허용과 확인 창을 거친다 (`docs/구조.md` 정한 것).

배포판이 설치돼 있거나 Release 빌드가 있으면 `open "jejari://…"`이 그 앱을 하나 더 띄울 수 있다. 개발 빌드로 보내려면 앱을 지정한다: `open -a build/Build/Products/Debug/Jejari.app "jejari://status"`

| 명령 | 하는 일 |
|---|---|
| `save?name=` / `restore?name=&mode=full\|arrange` / `undo` | 저장, 불러오기, 되돌리기 (확인 창 없이) |
| `verify?name=` | 옮기지 않고 저장된 자리와 다른 창만 보고 |
| `collapse` / `wipe` | 한 화면으로 모으기 / 깨끗하게 비우기 (확인 창 없이) |
| `late` | 늦게 떴지만 가상화면을 바꿔야 해서 기다리는 창을 옮김 (알림을 누른 것과 같음) |
| `status`, `grant`, `open?window=` | 설정 점검 결과, 권한 요청, 창 열기 |
| `scramble` | 창 몇 개를 일부러 흐트러뜨림 (개발 빌드만) |
| `replay` / `replay?clues=1` | 지난 불러오기 기록으로 짝짓기를 다시 돌려 그때와 다른 짝을 보여 줌 / 창 번호 없이 단서로만 (개발 빌드만) |
| `debuglate` / `debuglate?stop=1` | 늦게 뜰 창 지켜보기 상태(메뉴 맨 위 줄에 쓰는 값) / "그만 기다리기" (개발 빌드만) |
| `debugscan?app=`, `debugdrag`, `debugvd`, `debugremove`, `debugwindows` | 앱 창 분류, 끌어서 옮기기, 임시 모니터 경유, 가상화면 삭제, 자기 창 목록 (개발 빌드만) |

시험 순서의 예: `save` → `scramble` → `verify`(다름이 잡히는지) → `restore` → `verify`(전부 제자리인지).

시험 전에 `~/Library/Application Support/Jejari/`의 `logs/`, `snapshots/직전 상태.json`, `matches.json`을 백업하고 끝나면 되돌린다. 기록은 최근 20개만 남아 시험 불러오기가 쌓이면 실제 기록이 밀려난다.

늦게 뜨는 창 시험은 시험 앱 LateWin으로 한다 (`scripts/latewin/build.sh`, 사용법은 그 파일 머리말). 시험 배치에서 LateWin 말고는 모두 빼 두면 다른 앱을 건드리지 않는다.

- 불러오는 중에 뜸: `delay` 12 → ② 전체 복원이 창이 뜨는 대로 옮기는지
- 끝난 뒤에 뜸: `delay` 50 이상 → 불러오기는 "없음"으로 끝나고, 창이 뜨면 기록 폴더의 `late.json`에 "옮김"
- 끝난 뒤 다른 가상화면: 배치의 목표를 지금 보이지 않는 가상화면으로 바꿈 → `late.json`에 "누를 때까지 기다림", `late`를 보내면 옮김

불러오기 기록(개발 빌드는 기본으로 남김, 배포판은 설정에서 켤 때만)은 `~/Library/Application Support/Jejari/logs/<시각>-<배치>/`에 남는다.

| 파일 | 내용 |
|---|---|
| `snapshot.json` | 불러온 배치 (그때의 것. 나중에 다시 저장해도 그대로) |
| `before.json` / `after.json` | 불러오기 직전 / 끝난 뒤의 창 |
| `report.json` | 결과, 진행 기록, 짝(`matches`: 저장 창 번호 → 창 번호, 점수. 1000은 창 번호로 짝지은 것), 단계별 시간(`timings`) |
| `late.json` | 끝난 뒤 지켜보기에서 늦게 뜬 창을 옮겼는지, 누를 때까지 기다리는지 |

결과가 이상하면 before와 after를 비교한다. 짝짓기 규칙을 바꿀 때는 바꾸기 전후로 `replay`를 돌려 지난 기록에서 짝이 바뀌는지 본다. 창 번호로 짝지은 기록(점수 1000)은 정답이라 `replay?clues=1`의 다름이 곧 단서 짝짓기가 틀린 수다.

## macOS 업데이트 뒤 확인

비공개 API를 쓰므로 macOS를 올리면 다음을 확인한다.

- 설정 → 권한과 macOS 설정에서 "가상화면(Spaces) 기능"이 사용 가능인지
- `save` → `scramble` → `restore` → `verify`가 전부 제자리인지
- 모니터가 1대일 때 임시 가상 모니터를 거친 이동이 되는지
- Mission Control로 가상화면 추가·삭제가 되는지 (`debugremove`)
